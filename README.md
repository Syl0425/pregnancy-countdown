## 每次对话录入的固定处理流程

1. 把用户的自然语言事项转换为 `rule`；时间口径不明确时先问，不猜测。
2. 追加到 `data.json` 的 `items`，id 顺延为 `itm-XXXX`；对话直接录入时 `source` 填 `kimi`，关键检查项设置 `"milestone": true`。
3. 更新 `meta.updatedAt` 为处理当天日期。
4. 在项目目录运行 `./publish.sh`。脚本会重建两个 ICS、运行检查、提交并推送到 GitHub Pages，再核对公开 `data.json` 与本地完全一致。
5. 脚本成功后，回复用户：合并数量、计算出的绝对日期、公开页面和手机日历的更新状态；任何一步失败都要明确说明。

## 本机事项同步格式

页面「同步导出」继续生成 ` ```daopai-sync ` 代码块。这个名称只是既有数据协议标识，保持不改。

1. 用户把代码块直接粘贴到 Kimi 项目对话。
2. Kimi 解析 JSON，逐条分配正式 id，`source` 填 `phone`，追加进 `items`。
3. 更新 `meta.updatedAt`，运行 `./publish.sh`。
4. 回复「已合并 batch-xxx，共 N 条」；用户确认后可在页面清除已导出的本机事项。

## 手机订阅与主屏幕使用

1. 用 iPhone 的 Safari 打开公开页面，点底部「日历提醒」，再点「订阅」并确认「添加」。
2. 如果之前添加过旧订阅，先在系统日历中删除旧订阅，避免同一事项重复出现。
3. 关键里程碑可在同一弹层中再执行一次单次导入。
4. 在 Safari 中点「分享」→「添加到主屏幕」→「添加」。以后点主屏幕图标即可以独立窗口打开，不需要经过浏览器地址栏。
5. 浏览器本机事项按网站域名隔离；更换网址前，应先把旧页面里尚未合并的事项通过「同步导出」发给 Kimi。

## 修改锚点、知识或状态

- 改锚点：只改 `anchor.date`，必要时改 `anchor.type`，再全量重建日历。事项 UID 不变，避免重复日历事件。
- 导入知识：写入 `data.json` 的 `knowledge`，以周段 id 为键。
- 完成或废弃事项：把 `status` 改为 `done` 或 `archived`，保留记录但不进入页面与日历。

## 规则语法（rule）

`锚点前缀 + ± + 数字 + 单位`，区间用 `..` 连接两个片段。

- 前缀：`lmp`=末次月经第 1 天、`con`=受孕日、`due`=预产期。
- 单位：`D`=天、`W`=周、`M`=日历月。
- 示例：`lmp-3M`、`con+12W`、`due-4W`、`lmp+0W..due+0W`。
- 换算：`lmp = conception - 14 天`，`dueDate = lmp + 280 天`。

## 阶段与知识

- 一级阶段：备孕期、孕早期、孕中期、孕晚期、生产、产后 100 天。
- 孕早期：1–3、4–6、7–9、10–13 周。
- 孕中期：14–17、18–21、22–25、26–27 周。
- 孕晚期：28–31、32–35、36–39、40 周。
- 孕 1 周按 `0+0 至 0+6` 计算；周段边界必须与 `index.html` 的 `PERIODS` 一致。
- 每段知识包含 `mother`、`baby`、`nutrition`、`avoid`、`notes` 五个数组。
- 跨周区间事项显示在所有日期范围重叠的周段中。

## 日历与隐私注意事项

- iPhone 订阅日历由系统按自己的频率拉取，并非实时推送；关键提醒可再导入 `milestones.ics`。
- 浏览器 localStorage 可能被清理，重要本机事项应及时发给 Kimi 合并。
- 公开日历链接通常没有访问鉴权，标题和备注中不要写敏感信息。
